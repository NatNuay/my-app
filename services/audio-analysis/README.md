# วิเคราะห์ไฮไลท์จากเสียง (ทดลอง)

ค่าเริ่มต้นใหม่เป็น **fast**: เปรียบเทียบรูปแบบเสียงซ้ำ ไม่ใช้ Demucs, Torch,
NATTEN หรือโมเดลที่ต้องดาวน์โหลดเพิ่ม ใช้ numpy/scipy และ FFmpeg ที่ติดตั้งไว้แล้ว
ตัวเล่นและเสียงที่ผู้ใช้ได้ยินยังมาจาก YouTube IFrame แบบเดิม
ไม่มีการบันทึกไมโครโฟนหรือขอแชร์แท็บ

**ผลโหมดเร็วคือ “ท่อนซ้ำที่อาจเป็นฮุค” ไม่ใช่การยืนยันว่าเป็นฮุค**
ท่อน verse/pre-chorus ก็อาจซ้ำได้ และเพลงที่เปลี่ยนเรียบเรียงหรือร้องต่างกันมากอาจตรวจไม่พบ
ไม่อนุมานว่า instrumental break เป็น dance-break

## ผู้ใช้ที่ติดตั้งตามขั้นตอนเดิมแล้ว

ไม่ต้องติดตั้งโมเดลหรือแพ็กเกจเพิ่ม อัปเดตโค้ดแล้วเปิดตัววิเคราะห์ใหม่ใน Ubuntu:

```bash
source ~/muverse-audio/.venv/bin/activate
cd /mnt/c/Users/NatNuay/Downloads/my-app-personal
python services/audio-analysis/server.py
```

ถ้าเก็บโปรเจกต์ไว้ที่อื่น เปลี่ยน cd ให้ตรงโฟลเดอร์
ใน VS Code บน Windows เปิดโฟลเดอร์เดียวกัน เพิ่มใน `.env.local`:

```dotenv
AUDIO_ANALYSIS_URL=http://127.0.0.1:8765
```

แล้ว `npm run dev` และเปิด http://localhost:3100
เปิดทั้งสองหน้าต่างทิ้งไว้ เว็บเริ่มงานเมื่อเลือกคลิป ไม่ต้องกดวิเคราะห์
ตรวจบริการจาก PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/health
```

ต้องขึ้น version `fast-experiment-v1` และ engine `fast`
ถ้าเคยตั้ง `AUDIO_ANALYSIS_ENGINE=full` ไว้ ให้เปลี่ยนเป็น fast แล้วเปิดบริการใหม่

## ติดตั้งเฉพาะโหมดเร็วบนเครื่องใหม่

ต้องมี Python 3.11, FFmpeg, Node.js สำหรับเว็บ และเครื่องมือ Node.js/Deno ตามความจำเป็นของ yt-dlp
ไม่จำเป็นต้องลงชุดโมเดลหนัก:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r services/audio-analysis/requirements-fast.txt
python services/audio-analysis/server.py
```

## ขั้นตอนและเป้าหมายความเร็ว

1. yt-dlp ดึง audio stream ของคลิปเดิมลงไฟล์ชั่วคราว โดย fast ไม่สร้าง WAV เพิ่ม
2. FFmpeg ถอดรหัสเป็น mono 8 kHz ในหน่วยความจำ เฉพาะเพื่อวิเคราะห์ ไม่เปลี่ยนเสียงตัวเล่น
3. scipy/numpy คำนวณลักษณะเสียงทุก 0.5 วินาที แล้วเทียบช่วงซ้ำและจุดเปลี่ยนโครงสร้าง
4. ส่งช่วงที่มีหลักฐานซ้ำหลายรอบ พร้อมป้ายทดลอง ถ้าไม่มีหลักฐานก็ไม่สร้างช่วงขึ้นมา

เป้าหมายคือผลหลังเปิดคลิปไม่เกิน 30 วินาที รวมคิว/ดาวน์โหลด/API/UI
**ยังไม่มีผลทดสอบคลิป YouTube จริงครบวงจรบนเครื่องผู้ใช้ว่าเข้าเกณฑ์นี้**
การทดสอบเสียงสังเคราะห์ยาว 152 วินาทีให้ช่วงซ้ำ 3 รอบตรงกับจุดที่สร้างไว้
ขั้นคำนวณใช้ประมาณ 0.1 วินาทีบนสภาพแวดล้อมทดสอบ ไม่รวม YouTube/ถอดรหัส
ตัวเลขนี้ไม่ใช่การรับประกันเวลาและความแม่นยำของเพลงจริง

โหมดเร็วจำกัดงานรวมประมาณ 27 วินาที (รวมเวลาคิว), ดาวน์โหลด 12 วินาที,
ถอดรหัส 8 วินาที เว็บถามสถานะทุก 2 วินาทีและหยุดรอเมื่อเกินประมาณ 30 วินาที
การหมดเวลาเป็นผลไม่สำเร็จ ไม่ถือว่าทำตามเป้าหมายความเร็วสำเร็จ
งานที่ไม่ได้ถามสถานะนาน 8 วินาทีจะหยุด/ข้าม เพื่อลดคิวจากคลิปเก่า

## เทียบผลกับไฟล์เสียงเดิมโดยไม่ดาวน์โหลดซ้ำ

```bash
python services/audio-analysis/benchmark.py ~/muverse-audio/test-audio.wav --engine fast
```

แสดง engine, เวลาวิเคราะห์ และช่วงที่พบเป็น JSON
การทดสอบนี้ไม่รวมเวลา YouTube/คิว/API/UI จึงเป็นเพียงส่วนหนึ่งของเกณฑ์ 30 วินาที
ต้องฟังตรวจต้น–ท้ายช่วงและเพลงหลายแบบก่อนสรุปความแม่นยำ
ไม่มีเวลา/ชื่อเพลงเฉพาะใน detector

## เก็บผลและพื้นที่ดิสก์

- เก็บเฉพาะ JSON ของช่วงเพลง 30 วัน ไม่เกิน 500 คลิปใน `~/.cache/muverse-audio`
  เปลี่ยนที่เก็บด้วย `AUDIO_ANALYSIS_CACHE`
- ผล fast กับ full ใช้ชื่อแคชคนละชุด ไม่เขียนทับกัน
  ถ้ามีผล full เดิมอยู่แล้ว จะใช้ผลนั้นก่อนโดยไม่เรียกโมเดลใหม่
- คำอธิบายแบ่งท่อนที่ชัดเจนจาก uploader/comments มีลำดับก่อนผล fast
- ไฟล์ดาวน์โหลด/ข้อมูลชั่วคราวถูกลบหลังจบ ยกเลิก หรือหมดเวลา
  ไม่ลบไฟล์นอกโฟลเดอร์ชั่วคราวของงาน
- ไม่ดาวน์โหลดไฟล์น้ำหนักโมเดลเพิ่มใน fast และไม่สร้าง WAV บนดิสก์เพิ่ม
  แต่การลบไฟล์ใน WSL ไม่ได้ทำให้ไฟล์ดิสก์เสมือนของ Ubuntu ย่อคืนพื้นที่ Windows ทันที

## ขอบเขตและการเชื่อมต่อ

- บริการ bind เฉพาะ 127.0.0.1:8765 (เปลี่ยนด้วย AUDIO_ANALYSIS_PORT)
- ถ้าต้องข้ามเครื่อง ต้องมี reverse proxy HTTPS และ AUDIO_ANALYSIS_TOKEN ทั้งสองฝั่ง
  ไม่เปิด Python port ต่อสาธารณะโดยตรง
- ก่อนเปิดเว็บสาธารณะต้องมี authentication/rate limiting ระดับ deployment เพิ่ม
  คิวจำกัดไม่ได้ป้องกันการใช้งานผิดวัตถุประสงค์ครบชุด
- WSL2 ปกติเชื่อมจาก Windows ไป Linux ผ่าน localhost ได้
  ถ้า health ติดต่อไม่ได้ ให้ตรวจ localhost forwarding ก่อนเปลี่ยน bind
- ทำงานทีละ 1 คลิป รอได้ไม่เกิน 8 งาน เก็บสถานะใน RAM ไม่เกิน 128 รายการ
- รับคลิปไม่เกิน 15 นาที ไม่รับ live จำกัดไฟล์ 100 MB เมื่อ yt-dlp ตรวจขนาดได้
- YouTube อาจบล็อกการดึงเสียงได้ ไม่ข้ามข้อจำกัดเครือข่าย/ล็อกอินอัตโนมัติ
- ใช้กับคลิปที่มีสิทธิ์ดาวน์โหลดและวิเคราะห์ และตรวจเงื่อนไขแหล่งข้อมูล
- ต้องเป็น process ที่รันต่อเนื่อง ไม่ใช่ Next.js serverless อย่างเดียว

## กลับไปใช้โมเดลเดิม (full)

เฉพาะเครื่องที่ติดตั้ง All-In-One/Demucs/NATTEN ตาม upstream ครบแล้ว:

```bash
AUDIO_ANALYSIS_ENGINE=full python services/audio-analysis/server.py
```

Full ใช้ harmonix-fold0 บน CPU ตามค่าเดิม จำกัด 180 วินาที ไม่อยู่ในเกณฑ์เร็ว 30 วินาที
ใช้ AUDIO_ANALYSIS_THREADS ปรับจำนวนเธรด (ค่าเริ่มต้นไม่เกิน 6 ตาม CPU ที่จัดสรร)
AUDIO_ANALYSIS_DEVICE=cuda ต้องมี NVIDIA GPU กับ PyTorch/NATTEN ที่รองรับ CUDA จริง
AMD Radeon 840M ของเครื่องผู้ใช้ใช้ CUDA ของชุดนี้ไม่ได้โดยตรง
ไม่ควรติดตั้ง CUDA package เพื่อหวังให้ AMD GPU ใช้โมเดลนี้ได้

ผล full ที่ผู้ใช้รายงานสำหรับ ZovUnDFt0wI:
แยกเสียง 100.45s, เตรียมข้อมูล 2.56s, โหลดโมเดล 0.55s, inference 51.39s, รวม 164.1s
นี่คือเหตุผลที่ทดลอง detector เบาแทน การเปลี่ยน timeout/แคชไม่ทำให้คลิปใหม่ผ่านเกณฑ์
progress bar ของ All-In-One แสดงแค่ช่วง inference ไม่ใช่เวลารวมทั้ง pipeline

โมเดล full มีข้อกำหนด license แยกจากโค้ด เช่น madmom models ระบุ non-commercial
ตรวจใบอนุญาต dependencies/models ก่อนใช้งานเชิงพาณิชย์
